# Loop Engineer

Turn an authorized outcome into a bounded cycle of attempts, observations, and causal repairs. The domain skill owns creative requirements and user review stages; this skill owns execution, delegation, and evidence. Improving the process does not expand the user's requested deliverable.

## Establish the current contract

Use the latest user instructions and accepted artifacts to state the outcome, scope, constraints, acceptance criteria, available verification methods, and next permitted action. Reuse the project's existing current-state record. Put its current values first and historical notes below; resolve contradictions against actual user messages and files.

For each critical criterion, specify an observable result and the evidence needed to assess it. Keep three distinct states: **pass**, **fail**, and **unverified**. A tool returning successfully proves that the operation returned, not that the user's outcome passed.

Scale the record to the work. A small repair needs its defect, source version, acceptance evidence, and next action. A batch needs stable unit IDs and a shared contract revision. Link existing artifacts instead of copying the entire conversation into every handoff.

## Run the loop

1. **Choose the smallest useful attempt.** For a new provider, format, or workflow, complete a representative risky unit through actual input selection, generation, download, and inspection before expanding to a batch. Reuse a verified pilot while its relevant inputs and settings remain valid.
2. **Inspect the artifact.** Compare the real result with every critical criterion. Record the file/version and exact observation, location, or timecode. Keep absent evidence unverified. An independent review is useful only when the reviewer can inspect the relevant artifact and modality.
3. **Repair the cause.** Identify what likely caused the failed criterion and change the smallest relevant input or method. Preserve accepted work. Verify the repaired criterion and affected boundaries; check for regressions introduced by the repair.
4. **Integrate and continue.** Keep the selected artifact, rejected alternatives, checks, and remaining work traceable. When a unit passes, advance toward the requested deliverable rather than ending with a successful experiment. Recheck the assembled output because independently passing units may still conflict.

When two successive attempts fail to improve the same defect, stop repeating that method. Inspect the evidence, change a causal assumption, or delegate diagnosis before another attempt. This is a method change, not completion or a reason to abandon independent authorized work.

Keep an explicit attempt/time/credit ceiling appropriate to the task and within existing authorization. Reuse authorized tool tiers and budgets. Ask only for a material unapproved purchase, increase, or scope change. A new angle, worker, or method does not reset spent resources. Track pending job IDs; inspect their status before resubmitting and back off when nothing changes.

At a genuine limit, preserve results and continue independent work. State the exact unresolved criterion and the missing capability or decision. Follow service restrictions and use supported alternatives within the accepted intent; a different story, quality level, or deliverable needs the applicable user decision.

## Route work by responsibility

The user's explicit model choice for the current chat takes precedence. Prefer the following models for delegated work when these exact IDs are available; use supported reasoning levels appropriate to the task. This is task routing, not permission to change the chat's model or global settings.

| Responsibility | Preferred model | Useful boundary |
| --- | --- | --- |
| Plan execution, operate tools, maintain current state, integrate and deliver | `gpt-6.1-sol` | Own the workflow and validate worker outputs. |
| Extract facts, inventory files, run deterministic checks, inspect narrowly scoped evidence | `gpt-6-luna` | Clear inputs, criteria, and compact evidence; no creative reinterpretation. |
| Diagnose ambiguous recurring failures, resolve conflicting requirements, review difficult story or continuity decisions | `gpt-6-astra` | Send the difficult question and relevant artifacts, not the entire routine workload. |

Keep tiny tasks local when dispatch and review cost more than doing them. Parallelize independent work; serialize dependencies and shared mutations. A stronger model is useful for a harder decision, but does not supply a missing tool or evidence modality.

Send each worker: scope and contract revision, exact input paths, allowed writes, required checks, evidence format, and stop condition. For a different-model worker, use a fresh or limited context packet if required by the tool; preserve the minimum user constraints and approvals it needs. If model selection is unavailable, use the available agent and report the limitation only when it affects the work.

Assign one operator to a shared browser session or other stateful UI, and one writer to each shared output. Other workers analyze supplied artifacts or produce separate outputs. Return findings with evidence rather than only a verdict. For independent QA, supply raw requirements and artifacts without leading with the creator's conclusion. The owner resolves disagreements and remains accountable; worker consensus does not replace missing evidence or user approval.

## Finish and learn

Call work complete only when the requested artifacts exist, critical criteria pass on the current versions, and the required integration checks are evidenced. A review copy may be useful before then, but the handoff must name the remaining checks or defects. Run domain validation tools where provided and preserve their actual result; they certify only the properties they inspect.

Record a reusable lesson after a failure is observed and its repair is verified. Store project-specific facts in that project. Change shared skills only when authorized or clearly within a requested workflow improvement, and keep the correction narrow. Test a changed rule on a realistic case without giving the evaluator the intended answer.
